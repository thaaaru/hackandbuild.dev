OWASP Top 10 for LLM Applications

The 10 Most Critical Security Risks (2023 v1.0)

What is this?

The OWASP Top 10 for Large Language Model (LLM) Applications is a project that identifies and ranks the most critical security vulnerabilities found in applications that use LLMs. This list serves as an essential guide for developers, security professionals, and organizations to understand and mitigate the unique risks associated with this rapidly evolving technology.

What it is:

Manipulating an LLM through "crafty inputs" (prompts) to cause unintended actions. This can be done directly by overwriting system prompts or indirectly by hiding instructions in external data sources (like webpages or documents) that the LLM processes.

Examples & Attack Scenarios:

  • An attacker's direct prompt makes a support chatbot reveal customer data.
  • A user asks an LLM to summarize a webpage that contains a hidden instruction telling the LLM to send data to the attacker.

Prevention Methods:

  • Enforce privilege controls (human-in-the-loop for sensitive actions).
  • Clearly segregate external content from user prompts.
  • Establish trust boundaries between the LLM and external sources.

What it is:

This occurs when an LLM's output is accepted without proper scrutiny or sanitization and is passed directly to backend systems or frontend code. This can lead to classic web vulnerabilities.

Examples & Attack Scenarios:

  • LLM output containing JavaScript is rendered in a user's browser, leading to Cross-Site Scripting (XSS).
  • LLM output with a malicious SQL query is passed to a database.
  • LLM output is passed directly to a system shell, resulting in Remote Code Execution (RCE).

Prevention Methods:

  • Apply proper input validation on the responses coming from the LLM.
  • Encode all output from the model before rendering it back to the user.
  • Treat LLM output as untrusted user input.

What it is:

Manipulating the model's training data or fine-tuning process to introduce vulnerabilities, backdoors, or biases. This compromises the model's security, effectiveness, or ethical behavior from the start.

Examples & Attack Scenarios:

  • An attacker creates malicious documents and gets them included in the model's training set.
  • The model trains on falsified or unverified data, leading it to produce biased or incorrect outputs.

Prevention Methods:

  • Verify the legitimacy and source of all training data.
  • Use strict vetting and input filters for training data sources.
  • Craft different models with separate, purpose-specific training data.

What it is:

Attackers make the LLM perform resource-heavy operations, leading to service degradation (slowness) and high costs for the application owner. This is magnified because LLM operations are already very resource-intensive.

Examples & Attack Scenarios:

  • Sending queries that are unusually resource-consuming (e.g., asking for complex, long-form text repeatedly).
  • Overwhelming the LLM with input that exceeds its context window.

Prevention Methods:

  • Implement input validation and cap resource use per request.
  • Enforce API rate limits for individual users or IP addresses.
  • Limit the number of queued actions or total actions a user can trigger.

What it is:

The LLM application's lifecycle is compromised by vulnerable components. This includes using third-party datasets, pre-trained models, and plugins that may have their own security flaws.

Examples & Attack Scenarios:

  • Using an outdated or unmaintained third-party package (e.g., a vulnerable Python library).
  • Fine-tuning with a pre-trained model that was poisoned.
  • Attackers tricking developers via a compromised package on PyPi.

Prevention Methods:

  • Vet all data sources and use trusted, audited plugins.
  • Use model and code signing for external models.
  • Implement monitoring for vulnerabilities and maintain a patching policy.

What it is:

The LLM inadvertently reveals confidential data in its responses. This can include trade secrets, personal data, or proprietary algorithms that it learned during training, leading to data leaks and privacy violations.

Examples & Attack Scenarios:

  • The model overfits or "memorizes" sensitive data from its training set and repeats it.
  • A legitimate user is accidentally exposed to another user's data.
  • Crafted prompts bypass filters to reveal sensitive data.

Prevention Methods:

  • Use data sanitization and scrubbing techniques on training data.
  • Implement robust input validation and output filtering.
  • Apply the rule of least privilege when training models (don't train on data it doesn't need).

What it is:

LLM plugins (extensions that let the LLM interact with other systems) can have insecure inputs and insufficient access control. This allows attackers to exploit them to perform unintended, harmful actions.

Examples & Attack Scenarios:

  • A plugin accepts free-form text input, allowing an attacker to pass raw SQL or code.
  • A plugin has authentication but no authorization, allowing any authenticated user to access any function.

Prevention Methods:

  • Enforce strict, parameterized inputs (no free-form text into sensitive functions).
  • Conduct thorough security testing (SAST, DAST) on plugins.
  • Require manual user authorization for actions taken by sensitive plugins.

What it is:

The LLM-based system is granted excessive functionality, permissions, or autonomy, allowing it to perform actions that lead to unintended consequences. It's "too helpful" and can be tricked into misusing its power.

Examples & Attack Scenarios:

  • An LLM agent has access to unnecessary functions from a plugin.
  • A plugin has unneeded permissions on other systems (e.g., admin rights).
  • A personal assistant app with excessive permissions is tricked by a malicious email into sending spam.

Prevention Methods:

  • Limit plugins and tools to the minimum necessary functions.
  • Avoid open-ended functions; use granular, specific functions.
  • Require human approval for all sensitive actions and track user authorization.

What it is:

Systems or people depending too much on LLMs without proper oversight. This can lead to misinformation, legal issues, and security vulnerabilities due to incorrect, inappropriate, or insecure content generated by the LLM (e.g., "hallucinations").

Examples & Attack Scenarios:

  • An LLM provides incorrect or nonsensical information that a user trusts.
  • An LLM suggests insecure code, and a developer copies/pastes it directly into production.
  • A developer unknowingly integrates a malicious package suggested by the LLM.

Prevention Methods:

  • Regularly monitor and review LLM outputs.
  • Cross-check LLM output with trusted sources (human-in-the-loop).
  • Clearly communicate the LLM's risks and limitations to users.
  • Establish secure coding practices for all developers.

What it is:

Unauthorized access, copying, or exfiltration of proprietary LLM models. This is a significant risk due to the high cost of training models, and it can lead to economic loss and compromised competitive advantage.

Examples & Attack Scenarios:

  • An attacker gains unauthorized access to the LLM model repository.
  • A disgruntled employee leaks model artifacts (weights, data).
  • An attacker creates a "shadow model" by repeatedly querying the API to extract its logic.

Prevention Methods:

  • Implement strong access controls, authentication, and monitoring.
  • Implement rate limiting on API calls to prevent rapid querying.
  • Use watermarking frameworks in the LLM's lifecycle.
